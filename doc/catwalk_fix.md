## ⑥ 为什么偏置窗口在这套规划器里会崩（机制，实测支撑）

1. **候选角永远相对「支撑脚当前朝向」**（`walk_candidates`，`robot.cpp:676` / Rust 同名函数），
   而**新脚朝向被直接设成该步向**（`next()`：`stride >= active_distance` 时 `rz = 步向`，恒成立）。
   ⇒ 支撑脚朝向 = 上一步步向，于是窗口的参考系本身随每一步转动。
2. 无偏窗口下这没问题：`find_target` 取「离引导点最近」，步向 ≈ 指向引导点的方位，朝向自然锚在前进方向上。
3. 偏置窗口把步向单侧截断（左 `[−75°,0°]`、右 `[−10°,+65°]`，步进 π/12 的网格相位决定了末点，见 `robot.cpp:716-722`），
   于是**允许的步向可以离引导方位很远**；当引导点落在被禁止的一侧时，`find_target` 只能取窗口边缘，
   实测出现过「引导方位 100.8°，左脚窗口 [−75°,0°]，选中 θ=0°——脚朝背离引导点的方向迈」。
4. 参考系随步向转动 + 步向可大幅偏离前进方向 ⇒ 双足朝向进入正反馈：
   步 1A+偏置实测同足步向在 **−97° / +83° 之间以 180° 来回振荡**；步 1B+偏置实测退化为固定方向行军。
5. `guide_bias`/`arc_guide` 只改变「瞄准点」，不改变第 3 条的窗口参考系，因此**接上去也救不回来**（§⑤）。

**结论**：这不是「接线姿势不对」，是**设计层缺件**——偏置窗口需要一个新的锚（把窗口参考系锚到前进方向），
或者需要一个显式的横向间距目标（原 `ideal_walk`，`robot.cpp:72-132`，同样是零调用）。
这两条都超出 task-18 的写域与「不要改 route」的边界，建议单开任务。

## ⑦ T6 期间发现的阻塞缺陷（转 task-19）

**缺陷**：`Robot::satisfy_turn`（`robot.rs`，忠实移植 `src/robot/robot.cpp:232-235`）用
`atan2(...) − support.rz` 判角，**不做角度归一化**。当 `support.rz` 接近 ±π 时，
«候选方向 = support.rz + θ» 会被 `atan2` 折回 (−π, π]，差值变成 −345° 这类值，恒判失败。

**实测证据**（修复前状态）：

- `(700,700)->(900,1200)` 在 14 个 seed（0/1/2/3/5/7/11/13/42/99/123/777/2024/31337）上**全部 exit=2 NoPath**；
  `(0,0)->(900,1200)` 同样 exit=2；而 `(500,500)->(900,1200)`、`(100,100)->(900,1200)`、
  `(700,700)->(800,800)`、`(900,1200)->(700,700)` 均 exit=0。⇒ 与起点/路线有关，不是目标本身不可达。
- 加临时探针定位：NoPath 来自 `walk_to → find_target` 的**空候选集**（不是 `scale_star`）。
  失败姿态：swing=(679.921,825.350) rz=2.8473 rad(163.14°)，support=(670.520,812.409) rz=3.1091 rad(178.14°)。
- 用已验证的几何模型对该姿态复算：`satisfy_spacing` 在 θ>0 一侧本来可行（r=38、θ=+45° 时 spacing=9.302 ∈ [2,10]），
  但 `satisfy_turn` 全部为假；最大未归一化角差实测 **−345.00°**（r=24、θ=+15°），归一化后应为 +15°。
- 与任务描述里的 −348.5° 属同一现象（我这次抓取的姿态与候选点略有差异）。

**为什么没在 T6 里修**：改它会让 golden 夹具 `tests/golden/satisfy_turn.csv` 的 3 行（case 16/24/26）翻转
（raw −342.0° / +301.6° / +295.8° → 归一化 +18.0° / −58.4° / −64.2°，判据结果由 false 变 true），
而夹具在禁改区；且会污染猫步修复的归因。按 Lead 裁决转 task-19。

**旁证（不计入判据）**：书账修正后我复测这两个组合，`(700,700)->(900,1200)` 与 `(0,0)->(900,1200)` 都变成 **exit=0**——
因为轨迹变了，不再走到「支撑脚朝向 ≈178°」那个姿态。**这不代表缺陷已修**：缺陷仍在函数里，golden 3 行仍会翻转。

另：`--start` 保真度（C++ 的 `main` 读了 start 却从不传给 `find_path`，C++ 基线实际从 `Robot` 默认位姿起步）
按 Lead 裁决同样归 task-19，本任务未查。
